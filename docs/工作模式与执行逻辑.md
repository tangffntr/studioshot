## 1. 总体架构与模式分发

### 1.1 统一入口

所有出图任务统一从 `POST /api/jobs` 创建（`routes/index.ts:48-69`），请求体经 Zod 校验（`shared/src/schemas/api.ts:23-37`），核心字段：

| 字段 | 说明 |
|---|---|
| `instruction` | 用户文字指令 |
| `attachments[]` | 输入图的 mediaId 数组（产品图 + 素材图） |
| `templateId` | 模板 ID（有值 → 走 Pipeline 套图） |
| `mode` | 特殊模式标记：`video` / `tryon` / `batch-sku` / `scene-swap` |
| 其他 | `person`/`topGarment`/`bottomGarment`（试穿）、`referenceScene`/`skuProducts`（场景替换）、`duration`（视频） |

创建后立即返回 `jobId`，任务**异步执行**（`runJob(jobId).catch(...)`，admit-then-run 模式）。

### 1.2 模式分发（runner.ts）

`runJob()` 按 `payload.mode` + `payload.templateId` **顺序匹配、前命中即返回**（`runner.ts:24-132`）：

```
jobMode === "video"      → runVideoJob      (视频生成)
jobMode === "tryon"      → runTryonJob      (虚拟试穿)
jobMode === "batch-sku"  → runBatchSkuJob   (批量场景替换)
jobMode === "scene-swap" → runSceneSwapJob  (单图场景替换)
templateId 有值           → runPipelineJob   (模板套图)
以上都不命中              → runAgentLoop     (Agent 聊天对话出图，默认)
```

**续接对话**（`POST /api/jobs/:id/continue`，`index.ts:71-128`）不创建新 job，而是复用原 job，注入 `previousMessages`（历史）、`lastGeneratedMediaId`（上轮生成图）、`continuationInstruction`（本轮指令）。

### 1.3 续接对话的输入处理

```ts
// index.ts:93 — 取上一轮最后一张生成图
const lastGeneratedMediaId = lastMediaIds[lastMediaIds.length - 1];
// 若用户没传新图且 useLastGenerated=true → 自动用上轮图
if (useLastGenerated && finalAttachments.length === 0 && lastGeneratedMediaId) {
  finalAttachments = [lastGeneratedMediaId];
}
```

## 2. Agent 模式（聊天对话出图）

**核心特点**：由主 LLM（orchestrator/vlm 槽）自主决策，调用工具完成任务。**文生图 vs 图生图不是代码分支，而是同一个 `generate_image` 工具靠 `referenceMediaIds` 是否为空来区分，分流决策权完全交给主 LLM**（由 SYSTEM_PROMPT 引导）。

### 2.1 SYSTEM_PROMPT 的行为分流（loop.ts:29-76）

SYSTEM_PROMPT 引导主 LLM 在三种行为间决策：

- **用户给了产品图**（消息含 media id 或图片）→ 先 `analyze_product` 分析，再 `generate_image` 出图（图生图，带参考图）
- **用户没给图、只是描述**（如"生成一只猫"）→ 直接 `generate_image`，**不传 referenceMediaIds**（纯文生图）
- **用户只是聊天**（不需要图）→ 直接文字回复，不调任何工具

**多图融合规则**（loop.ts:36-41）：用户消息可能含多张图——第 1 张是**产品图**（主图，必须外观保真），其余是**参考素材图**（场景/背景/模特/风格）。生成时必须把"产品图 + 所有参考素材图"都放进 `referenceMediaIds`。融合示例：产品图(杯子)+参考素材(窗台) → 杯子放进窗台。

**续接对话规则**（loop.ts:43-47）：当消息含"重要提示：上面是上次生成的产品图片"时，必须把指定 mediaId 放入 `referenceMediaIds`；即使只说"换个背景"也要带上参考图。

### 2.2 消息构建：新对话 vs 续接

**新对话模式**（loop.ts:204-247）：
1. 首条为 system prompt
2. 多图融合：把 `initialMediaIds` 每个 id 经 `readMediaBase64` 读成 base64，拼成多模态 `image_url` 喂给主 LLM
3. 区分角色：第 0 张标"产品图"，其余标"参考素材N"，让 LLM 明确每张图的作用
4. 图片全部读取失败则退化为纯文本

**续接模式**（loop.ts:169-202）：
1. 复用 `previousMessages` 历史消息
2. 把 `lastGeneratedMediaId` 读成 base64 多模态图推入 user 消息（让 LLM"看见"上轮图）
3. 紧跟一条**强约束文本**：明确要求把该 mediaId 放入下次 `generate_image` 的 `referenceMediaIds`

### 2.3 可用工具（共 3 个，registry.ts:10-14）

| 工具 | 作用 | 模型 | 文件 |
|---|---|---|---|
| `generate_image` | 生图（文生图/图生图），回灌图片让主 LLM 看回图 | main-image 槽 | tools/generate-image.ts |
| `analyze_product` | VLM 分析产品属性，返回结构化 JSON（类目/颜色/材质/卖点/描述） | vlm 槽 | tools/analyze-product.ts |
| `check_quality` | VLM 质检生成图，返回 score/passed/issues | vlm 槽 | tools/check-quality.ts |

### 2.4 工作流

**有产品图**：`analyze_product`(只调1次) → `generate_image` → `check_quality` → 通过则结束，不通过最多重试1次。

**无产品图**：直接 `generate_image`(referenceMediaIds 传空数组) → `check_quality` → 结束。

**收敛规则**：最多生成 2 张图后必须文字总结结束；循环硬上限 25 步（loop.ts:27）。

### 2.5 文生图 vs 图生图对照

| 维度 | 文生图 | 图生图 |
|---|---|---|
| 触发条件 | 用户只描述、未给图 | 用户给了产品图/素材，或续接对话 |
| `referenceMediaIds` | 空数组 `[]` | 含产品图 + 所有参考素材图 |
| 前置动作 | 无 | 通常先 analyze_product |
| facade 参数 | `referenceImages: []` | `referenceImages: [base64...]` |
| 目标 | 按描述自由生成 | 产品外观保真 + 融合参考素材 |

## 3. Pipeline 模式（模板套图出图）

**核心特点**：确定性流水线（无 LLM 自主决策），适合一次生成整套图（如亚马逊 PDP 的 14 个图位）。

### 3.1 执行阶段（pipeline.ts:132-425）

| 阶段 | 做什么 | 调用 |
|---|---|---|
| 1. 分析产品 | VLM 分析产品属性 | `analyzeForRender(sourceMediaIds[0])` |
| 2. 页面规划 | 生成 8 屏 blueprint，等用户确认（SSE 轮询 5 分钟） | `generateBlueprint()` |
| 3. 渲染 prompt | 模板骨架占位替换 | `renderAllSlots(slots, attrs)` |
| 4. 风格锁 | 给每张图 prompt 加统一风格前缀 | `applyStyleLock()` |
| 5. 读参考图 | 产品图+全部素材图读成 base64 | `readMediaBase64()` |
| 6. 网格生成 | 按图位分组，拼网格大图生成 | `generateGridPrompt()` + facade |
| 7. 后端切割 | 网格大图切割成单张子图 | `oss.cutGridImage()`（sharp） |
| 8. 文字叠加 | 子图按需叠中文文字 | `addTextOverlay()`（sharp） |
| 9. 落库完成 | 建 media 记录 + 推完成事件 | DB insert |

### 3.2 提示词生成链路（skeleton → 最终 prompt）

```
模板骨架 "{color} {category}"（promptSkeleton）
  │
  ├─① 占位替换（render.ts:24-38，正则 /\{(\w+)\}/g）
  │   "{color}" → "红色"，"{category}" → "马克杯"
  │   缺失兜底：color→中性色, material→优质材质, category→产品
  │
  ├─② 风格锁注入（style-lock.ts:37-43，加前缀）
  │   "[风格锁定：色板+冷暖调+光线+构图+背景] 红色 马克杯"
  │
  ├─③ 网格 prompt 合并（pipeline.ts:80-96，按位置拼）
  │   "生成 2x2 网格图…上方左侧区域：[风格锁定…] 红色 马克杯…"
  │
  └─④ 送进生图 API
      Model.image(taskSlotKey).generate({ prompt: gridPrompt, referenceImages, size })
```

**注意**：①② 不调 LLM（纯字符串处理，省时省钱）；只有 ① 分析产品调 VLM。

### 3.3 网格合并 + 后端切割（性能优化）

同组（hero 主图组 / detail 详情页组）的多个图位拼进**一张网格大图**用单次 API 调用生成，再用 sharp 按均分坐标切割成子图（`oss.ts:89-119`）：
- hero 组：2x2 网格（4 张主图）
- detail 组：1x2 纵向拼接（2 张详情页）
- 超容量分批生成

### 3.4 多图融合参考（图生图）

**每一张网格大图都带全部参考图**：`referenceImages: refB64List`（产品图 + 所有参考素材图，`pipeline.ts:317-323`）。
- **属性识别只用第 1 张**（产品主图）：`analyzeForRender(sourceMediaIds[0])`
- **生图参考用全部**：保证不同组之间产品外观一致

### 3.5 Blueprint（页面规划）的作用

blueprint 是 8 屏详情页的结构化规划（卖点种子、各屏文案结构、视觉 DNA）。当前实际作用：
1. **面向用户的确认环节**：给用户看规划，确认/拒绝/重生成
2. **D 槽的尺寸/分组依据**：D 开头 slot 走 detail 组、3:4 宽高比

> 注意：blueprint 的卖点种子字段当前**尚未注入**实际生图 prompt（代码里埋了 `renderAllSlotsWithBlueprint` 能力，但主路径用的是不带 blueprint 的版本）。这是"设计 vs 实现"的差异点。

## 4. 视频生成模式（video）

**核心特点**：用 LLM 生成视频描述 prompt → 调视频模型（异步任务，提交+轮询）。

### 4.1 执行流程（video.ts:56-167）

1. **取首帧**：`firstFrameB64 = oss.getImageBase64(filePath)`
2. **VLM 分析产品**（ANALYZE_PROMPT）：输出 product/color/material/style/features
3. **生成视频 prompt**（VIDEO_PROMPT_TEMPLATE，用 orchestrator 槽）：填入产品信息+用户需求+时长
4. **调视频 API + 内容违规重试**：依次尝试 3 档 prompt（原始→简化→最简），命中 content_policy/400 才降级
5. **下载存 OSS 入库**

### 4.2 内容违规重试（3 档 prompt）

```ts
const promptVariants = [
  videoPrompt,                                                    // 原始
  `${productInfo}。白底产品展示视频，平稳旋转，专业光线。`,           // 简化
  `产品视频，展示${产品名}，干净背景，平稳运动。`,                    // 最简
];
```

### 4.3 视频适配器差异

| 适配器 | 图生视频 | 提交端点 | 轮询 |
|---|---|---|---|
| **Agnes**（agnes-video.ts） | ❌ 需公网URL，本地base64不支持，文生兜底 | `POST /v1/videos` | `/agnesapi?video_id=`，5s |
| **Kling**（kling-video.ts） | ✅ 支持首帧 base64 | `/v1/videos/image2video` 或 `text2video` | `/v1/videos/query/{id}`，8s |

帧数约束（Agnes）：`num_frames` 满足 8n+1 ≤ 441（合法值 81/121/.../441）。

## 5. 虚拟试穿模式（tryon）

**核心特点**：模特图 + 上下装平铺图 → 试穿效果图（阿里云 OutfitAnyone）。

- **输入**：模特图（必填）+ 上装图（可选）+ 下装图（可选）
- **输出**：1 张试穿效果图
- **适配器**：硬编码 `aliyun-tryon`（DashScope，异步任务）
- **promptText**：固定字符串 `"OutfitAnyone 试穿"`（非模板）

> 注意：阿里云官方要求图片为**公网 URL**，当前用 base64 data URL 兜底（生产需配 OSS 公网 URL）。

## 6. 场景替换模式（scene-swap）与批量 SKU（batch-sku）

**核心特点**：用 grsai 图生图（多参考图）实现"把自家产品放进对标场景"。

### 6.1 单图场景替换（scene-swap）

- **输入**：对标场景图 + 自家产品图
- **机制**：`referenceImages: [场景图, 产品图]`，prompt 要求"保持相同构图/光线/背景，仅替换产品主体"
- **可追加**用户 instruction

**SWAP_PROMPT_PREFIX**：
> "用提供的产品替换场景中的产品。保持完全相同的构图、拍摄角度、光线方向、色温和背景氛围，仅替换产品主体。新产品在现有场景中应显得自然融洽。"

### 6.2 批量 SKU（batch-sku）

- **本质**：对每个 SKU 各调一次场景替换，确定性循环
- **特点**：单张失败不中断（continue），结果汇总 `total` + `generated`
- **prompt**：更短固定版（不可定制）

### 6.3 两模式对比

| 维度 | scene-swap（单图） | batch-sku（批量） |
|---|---|---|
| prompt | 强调光线/色温/氛围，支持追加指令 | 更短固定，强调"光线和背景" |
| 循环 | 单次 | 多 SKU 逐个调用 |
| 失败处理 | 直接抛错 | 单个失败 continue，不中断 |
| slotCode | `SCENE-SWAP` | `SKU-{i+1}` |

## 8. 图片一致性机制总览

| 模式 | 一致性保障手段 |
|---|---|
| **Agent 续接对话** | 上轮生成图读成 base64 多模态输入 + 强约束文本要求放入 referenceMediaIds（双层保障） |
| **Pipeline 同组内** | 网格合并生成（同一张图渲染，天然一致）+ 网格 prompt 要求"统一风格光线" |
| **Pipeline 跨组** | 风格锁（每张 prompt 共享相同风格前缀）+ 每张图都带相同的产品参考图 |
| **scene-swap/batch-sku** | 同一母版场景图 + grsai 多参考图保真 |

**文生图与图生图的产品保真差异**：
- 文生图：无参考图，产品外观由 prompt 描述决定，保真度低
- 图生图：referenceMediaIds 带产品图，生图模型以产品图为参考，保真度高

## 9. 关键设计说明

### 9.1 文生图/图生图不是代码分支

Agent 模式下，二者是同一个 `generate_image` 工具，靠 `referenceMediaIds` 是否为空区分。决策权在主 LLM（SYSTEM_PROMPT 引导），不是硬编码 if/else。

### 9.2 工具结果回灌走 user role 而非 tool role

`loop.ts:326-332`：generate_image 生成的图以独立 `user` 消息（多模态）回灌，而非标准 `tool` role。原因：OpenAI 标准 tool message 不支持多模态 content，MiMo 等严格遵循标准的模型会报错。这是"看回图→判断→重试"闭环（A3 闭环）成立的关键工程细节。

### 9.3 readMediaBase64 支持 media + materials 双表

`generate-image.ts:24-33`：先查 `media` 表（产品图/生成图），回退查 `materials` 表（素材库素材）。素材有 filePath 但无 sourceMediaId 时，按 materials.id 也能读图作参考。

### 9.4 参考图压缩

grsai 适配器（`grsai.ts`）用 sharp 压缩参考图（长边 1024px + JPEG 85%）后再上传，避免原图过大（如 1.8MB）导致 "image upload failed"。

### 9.5 任务槽（task_slots）与模型路由

每个槽（main-image / detail-page / vlm / orchestrator / video）绑定一个主模型 + 可选备用模型。`resolveSlotWithBackup`（task-slots.ts:35-53）解析，主模型失败自动 fallback 备用模型。

### 9.6 设计 vs 实现差异点

- pipeline.ts 文件头注释（1-17行）描述的是旧版"逐 slot 串行"，实际函数体（132行起）是"网格合并+后端切割"。**以函数体为准**。
- blueprint 的卖点种子/文案结构字段尚未注入实际生图 prompt（`renderAllSlotsWithBlueprint` 未被调用）。
- 详情页（detail 组）实际宽高比是 3:4（size-resolver.ts:30），非部分注释写的 9:21。
